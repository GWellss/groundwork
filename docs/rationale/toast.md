# Toast rationale

For human contributors: why the spec is the way it is. Agents do not need this file.

| Decision | Reason |
|---|---|
| One component for toast, snackbar and flag | They differ by name and by small visual details, not by function: a short message that goes away. One spec avoids three look-alikes |
| Surface fill, following the theme mode, not the inverse fill | The toast is light in light mode and will be dark in a dark mode, because it uses the surface tokens like every other panel. The inverse fill is a fixed dark surface used by the tooltip; a second one would need a second set of rules for muted text and for buttons on a dark fill (buttons inside would have to be restyled). The surface keeps every button entry valid in any mode. No dark mode is created here |
| `level-3`, quiet border | The role of `level-3` is floating above content while it scrolls. A toast is not tied to a trigger, so it sits one level above the popover |
| Status shown by an icon only, `neutral`, `success`, `danger` | The toast stays on the surface, so its contrast stays that of the surface. The icon color is `success` or `danger`, which already reach 4.5:1 there (a new `success` accent on the surface, nothing off the surface). No `warning`: a warning must be read again, which is an alert |
| Default duration 6000 ms, minimum 5000 ms | WCAG 2.2.1 asks that time limits can be adjusted or extended; the toast pauses on hover and focus, and 5 to 6 seconds is the commonly accepted lower bound for a short sentence. The values are behavior constants, not theme tokens |
| No timer for a toast with an action or an error | A control that vanishes cannot be relied on: a keyboard or screen reader user may not reach it in time. Carbon says the same: an actionable notification does not disappear by itself ([Carbon notification usage](https://carbondesignsystem.com/components/notification/usage/)). This reverses an earlier rule of this kit (6 s for toasts with an action too). A message-only toast keeps the timer, otherwise toasts pile up and end up ignored; an error stays because it must be read |
| The action also exists elsewhere in the page (good practice, no longer a requirement) | A user who closes the toast loses nothing, and the toast stays a shortcut rather than the only path ([Adrian Roselli](https://adrianroselli.com/2020/01/defining-toast-messages.html)) |
| Timer cancelled for good once the toast takes focus | A user who reached the toast with the keyboard is reading or deciding; a timer that restarted on blur would remove it under them. This is how a user turns the limit off from the keyboard ([React Aria Toast](https://react-aria.adobe.com/Toast): pause on hover and focus, 5 s minimum) |
| Focus never moved to a toast; region named "Notifications", reached by `F6` / `Shift+F6` | `status` and `alert` messages are announced without taking focus ([WCAG 4.1.3 Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html), [Adrian Roselli](https://adrianroselli.com/2020/01/defining-toast-messages.html)); a landmark reached by a shortcut gives keyboard users access without stealing focus ([React Aria Toast](https://react-aria.adobe.com/Toast)). This differs on purpose from Carbon, which moves focus to the action: a focus jump interrupts what the user is doing and the toast is not a dialog |
| WCAG 2.2.1 (Timing Adjustable) verdict | [Understanding 2.2.1](https://www.w3.org/WAI/WCAG22/Understanding/timing-adjustable.html). Toasts with an action and `danger` toasts have no time limit: the criterion does not apply. Message-only toasts keep a limit of at least 5 s that the user can turn off by focusing the toast (`F6`) or pausing it with the pointer. That is a mechanism, but one reached inside the time limit, so the kit does not claim unconditional conformity for them: a project that must claim it sets `duration` to `none` or adds a user setting that turns the timer off |
| Pause also when the page is hidden, restart with the full duration | A toast that expires while the user is in another tab was never read; a partial remaining time after a hover is too short to be useful |
| Polite region present from the start, `role="alert"` on `danger` only | Live regions are announced reliably only if they exist before the content. Polite avoids interrupting; a failed action is the one case where interrupting is justified |
| Waits while a dialog is open | The page behind a dialog is inert, so a message there would not be announced |
| At most three visible, newest nearest the edge | A tall stack covers the page and floods screen reader users. Others queue |
| `bottom-center` by default, four placements | A common default, away from the floating button at the end of the bottom edge; one placement per page, so a user always looks in the same place |
| Reuses `floating-max-width` | One token for the width of every panel of this kind; a toast needing more is an alert |
